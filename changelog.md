## Poriscope 1.8.0: in progress

* **Docs: compliance-gate block 8 (custom lint rules) is closed without building anything**
    * The block proposed mechanically enforcing three conventions held by review attentiveness alone. All three are now resolved and none of them by writing the checker it asked for, so it is marked closed in `future_fixes.md` and removed from the queue at the top of that file rather than left sitting at position 2.
    * **The bare-`except:` half was already enforced, and had been all along.** The block asked whether `ruff` had a built-in rule and whether it was on; both are yes. `E722` is in Ruff's **default** rule set, and `pyproject.toml` uses `extend-select`, which *adds to* the defaults rather than replacing them - so the gate catches a bare `except:` even though no line of config names it. Measured rather than reasoned: a throwaway file containing one was placed under `poriscope/` and `pre-commit run ruff --files ...` failed it with `E722 Do not use bare except`. The "one-line config addition" the block held in reserve would have been a no-op.
    * The no-nested-functions half was dropped on 2026-09-01 with the convention change above. The sqlite-cleanup half was already deferred by the block's own reasoning into block 1's conformance suite, which is a pytest suite and therefore owned by another developer - it rides along with that whenever it is built and is not separate work.
    * `quality_control.rst`'s "Which rules are enabled" note is rewritten to say the defaults are in force on top of the selected rules, and names `E722` as the example that matters, since the previous wording ("On top of Ruff's default rule set, `pyproject.toml` selects...") left a contributor no way to know what the defaults covered. This is block 8's own step 4 - document whichever of these become real automated checks - discharged.
    * **Deliberately not added to `CLAUDE.md`.** Block 8's step 4 named that file, but it is loaded in full at the start of every session and should carry rules a human has to remember; a rule the gate enforces on every commit is not one of those.

* **Changed: the no-nested-functions convention is relaxed rather than absolute**
    * `CLAUDE.md` said "Do not nest functions inside other functions", with decorators as the only exception. It now permits a nested function **where that is genuinely the simpler option and the nested function is short and simple** - typically a small closure capturing a local so it can be handed to a callback, a timer or a signal. A hoisted method plus `functools.partial` is still the right answer when the closure grows, is reused, or needs testing on its own, and an existing one that reads well should not be "flattened". Decorators still always nest, for the closure they require.
    * No code changed, and nothing was broken: verified that no gate enforces the old rule (ruff selects only `I`, `B006`, `B020`), so the convention was carried by review attentiveness alone. The immediate case is `MultiSelectFilterComboBox._handle_internal_edit`, whose three-line `open_dialog_then_reopen` captures `name` for `QTimer.singleShot`; it stays as it is, and `test_edit_filter_callback_called` covers it.
    * **Block 8's no-nested-functions checker is dropped from `future_fixes.md`** rather than left queued. "Genuinely simpler, short and simple" is a judgement an `ast` walk cannot make - a checker would need a line-count or complexity threshold to approximate it, and would flag precisely the small callback closures now permitted. The rest of block 8 (no-bare-except, sqlite cleanup) is unaffected. Two other entries closed with it: the three nested definitions in the owner-held fitter files, and a `future_refactors_and_features.md` item whose only justification was the old rule.

* **Fixed: the `post-merge` hook selected whichever Python started first, which on Windows is the wrong one**
    * The hook is a `/bin/sh` shim that probes `python3`, then `python`, then `py -3`, and takes the first candidate that runs. The probe was `import sys; sys.exit(0)` - a test of whether the candidate is *a* Python, not whether it is *this project's* Python. Under Git Bash on Windows `python3` resolves to the MSYS2 interpreter, which starts perfectly well and has no numpy, PySide6 or sphinx, so it won on being first in the list. Every merge on such a machine ended with `sphinx ... returned non-zero exit status 1` and no autodoc regeneration. Found when `git flow feature finish` ran the hook after the event-filter fix below.
    * There is a mordant edge to it: the MSYS2 install that shadows `python3` is frequently one **this same hook put there**, since it installs MinGW to build the wavelet shared library.
    * The probe is now `import poriscope.exposed`. Verified to discriminate on the affected machine: the old probe selects `C:/msys64/mingw64/bin/python3.exe`, the new one selects the project interpreter. **`import poriscope` would not have worked** - `poriscope/__init__.py` wraps `from .exposed import *` in `try/except ImportError` so a half-installed dependency set cannot break `pip install`, so it succeeds even with numpy absent and *both* interpreters pass it. Importing the submodule directly is what proves the dependencies are really there. The probe now also runs from the repository root, so a working tree with its dependencies but no `pip install -e` still resolves.
    * **Worth knowing how far this reached.** Every sub-script propagates the shim's choice through `sys.executable`, so this was not only a broken docs build: `post-merge-update_requirements.py` runs `pip install -r requirements.txt`, and under the wrong interpreter that installs the project's dependencies into MSYS2's Python. That step is gated on `requirements.txt` having changed in the merge, so it appears not to have fired in practice - a latent hazard rather than damage already done, but the reason this is worth more than a one-line probe change.
    * When nothing passes the probe the hook now says so and skips, rather than proceeding under an interpreter that cannot import the project, and points at `pip install -e ".[dev]"`. `post_merge_automation.rst` gains a note explaining which interpreter is chosen and why the two obvious probes are both insufficient - the page previously just asserted "Ensures the correct Python interpreter is used", which was the one thing it was not doing.

* **Fixed: `pytest tests/unit` errored intermittently with "Internal C++ object already deleted", from event filters that were never removed**
    * `MultiSelectFilterComboBox` and `MultiSelectComboBox` each called `QApplication.instance().installEventFilter(self)` in `__init__` and nothing ever removed it - `removeEventFilter` appeared **zero** times in the repository. The application singleton outlives every widget, so each construction leaked a registration for the life of the process; once Shiboken tore down a widget's C++ object, the still-registered Python wrapper was called on the next event delivered *anywhere* and raised. A full `tests/unit` run built 150-200+ of these, an unknown fraction of them stale, which is why the reported victim was a different test each time. Measured on this branch before the fix: **1 error in 5 runs**, at `multiselect_filter.py:135` in `TestRelayQuery`, exactly as recorded in the handoff.
    * **The fix scopes the filter's lifetime, not its target.** It is now installed in `showPopup()` and removed in `hidePopup()`, so at most one exists at a time and only while a popup is actually open. Teardown happens with popups closed, so there is no registration left to go stale. `eventFilter` also self-heals: if it runs while the popup is not visible - reachable when the popup is closed by a path that bypasses `hidePopup()`, such as its own title-bar close button - it removes itself and returns.
    * **The handoff's suggested fix was measured and rejected.** It proposed scoping the filter to `containerWidget` or to `self`. That would have silently broken click-outside-to-close on Windows and macOS, and the Linux CI could not have caught it. The reason is that **`Qt.Dialog | Qt.Popup` is `Qt.Tool`**: window type is a value in the low byte of the flags word, not a set of independent bits, and `Tool == Popup | Dialog == 11`. Both widgets build their container as a `QDialog` with `Qt.Popup` OR-ed into the existing flags, so on those platforms it is a **tool window, not a popup** - `isPopup()` is false, Qt's popup mouse grab never engages, and a click elsewhere is never routed to the container, so a filter installed there would never see it. Only `multiselect.py`'s Linux branch, which *replaces* the flags with `setWindowFlags(Qt.Popup | Qt.FramelessWindowHint)`, produces a genuine popup. That asymmetry is very likely why the application-wide filter was written in the first place. Recorded in `DECISIONS.md` so it is not re-proposed.
    * **All three `eventFilter` implementations now `return False` instead of `return super().eventFilter(obj, event)`.** `QComboBox`, `QWidget` and `QLineEdit` do not reimplement `eventFilter`, so the inherited implementation is `QObject::eventFilter`, whose entire body is `return false` - the call was a round-trip into C++ that computed nothing. It was also *the* line in every recorded traceback, because it is the one statement on the fall-through path that needs a live C++ `self`. This is behaviourally identical and deletes the crash site.
    * **`BaseLineEdit` is fixed by that one line alone**, deliberately. Its filter genuinely has to be application-wide and application-lifetime - it watches for `QMessageBox` Show/Hide anywhere in the app to set a class-level `suspend_validation` flag - so it cannot be scoped the way the comboboxes were. But nothing in its body touches a C++ member of `self`, so with the base-class call gone, a stale registration is inert rather than fatal. Replacing its three per-instance registrations with a single application-owned watcher was considered and **not** done: it is a new class and a breaking change to something re-exported from `exposed.py`, to remove a leak that is bounded at 3 per controls build and has never been observed to crash.
    * **Not done, and why**: `containerWidget` is parentless in both widgets (`QDialog(None)`, `QWidget(None)` on Linux) and parenting it was in the plan, on the stated grounds that it would stop `tests/unit/views/conftest.py::_close_leftover_widgets` sweeping it as a top-level. **That rationale was measured and is false** - a parented widget that keeps its window flags is still returned by `QApplication.topLevelWidgets()`, so the sweep is unaffected either way. The change was dropped rather than kept on a rationale that does not hold; the remaining benefit is ownership tidiness and it is recorded in `future_fixes.md`.
    * 14 regression tests added, 7 to each widget's existing test file, all headless: no filter installed at rest (the direct encoding of the bug), installed while the popup is open, removed after `hidePopup`, an outside press closing the popup and being consumed, an inside press leaving it open, the self-heal, and a non-mouse event returning `False`. Verified to discriminate: run against the pre-fix code, the three lifetime assertions fail per widget while every behavioural one passes - which is also the evidence that behaviour is unchanged.
    * `event.globalPos()` became `event.globalPosition().toPoint()` in both filters. Not scope creep for its own sake: the new tests exercise that line and surfaced it as a `DeprecationWarning` in the suite output, and the replacement is covered by the inside- and outside-press tests above.
    * **Measured.** `pytest tests/unit` before the fix: **1 error in 5 runs**. After: **0 errors in 15 runs**. Fifteen clean runs against a 1-in-5 failure rate is a ~3.5% outcome by chance, so this is real evidence rather than a lucky sample - and the argument does not rest on it anyway, since the new regression test asserts the invariant directly (no filter installed at rest) and fails against the pre-fix code, meaning the failure mode is removed rather than made rarer.
    * No measurable performance change, despite the expectation of one. The first five post-fix runs averaged 60.6s against a 67.3s baseline, which looked like the ~10% win you would predict from an empty filter chain - every event delivered to every object had been walking 150-200 Python filters. Ten further runs averaged 68.5s, putting all fifteen at 65.9s against 67.3s: within noise. Recorded because the plausible-sounding speedup was measured and did not survive more data.

## Poriscope 1.7.1: 2026-08-31

* **Fixed: the documentation build failed on CI with several hundred `wrapper loop when unwrapping PySide6.QtGui` errors**
    * The `Build and Deploy Docs to Pages (main)` run immediately after `v1.7.0` failed under `-W`, with an `autodoc: failed to import` warning for essentially every documented member of every Qt-touching module. None of it reproduced locally, where the same build was and had always been clean.
    * The cause was that `docs/source/conf.py` set `autodoc_mock_imports = ["PySide6"]` while also importing `poriscope.constants` at the top of the file. Importing a submodule runs `poriscope/__init__.py` first, which does `from .exposed import *` and pulls in the real PySide6 - at conf-load time, long before autodoc installs its mock finder. Since `sys.modules` is consulted ahead of any meta-path finder, **the mock was inert on every machine where PySide6 imports cleanly**: the docs have always been built against the real library, and the setting did nothing.
    * On CI it was worse than inert. Neither docs workflow installed system libraries, so `import PySide6.QtCore` succeeded but `import PySide6.QtGui` failed on the missing `libEGL.so.1`, part-way through `exposed.py` at `poriscope/utils/BaseLineEdit.py`. That left the process with half of PySide6 real and half of it absent. autodoc then mocked the absent half, and the real half's shiboken import hook called `inspect.getsource()` on a Sphinx mock, whose `__wrapped__` chain never terminates - one `ValueError` per documented member. The warnings likely predate the `-W` gate added in 1.7.0; that gate is what turned them into a failed deploy.
    * **The mock is removed rather than completed.** Making it total is strictly worse, and this is measured rather than assumed: importing all 100 modules under `poriscope/` succeeds for 99 of them against the real library (the one failure, `poriscope/cdlls/wavelet/test.py`, is in no generated `.rst`) and for only 44 of them under a full mock, because the `functools.wraps` and `re` calls in `utils/DocstringDecorator.py` and `utils/LogDecorator.py` run against mock objects and raise `TypeError: __type_params__ must be set to a tuple`. `conf.py` now carries a comment recording all of this so the setting is not added back.
    * `docs-check.yml` and `build_and_deploy_docs.yml` each gained an `Install Qt native libs` step (`libegl1`, `libgl1`, `libxkbcommon0`) and `QT_QPA_PLATFORM: offscreen`. That list is not a guess: reading the `DT_NEEDED` entries out of the manylinux PySide6 6.9.0 wheel, those are exactly the libraries the bundled `libQt6Gui`/`libQt6Widgets`/`libQt6Svg` link against that the runner image does not already carry, and the loader resolves all three at import time - `libxkbcommon.so.0` included, despite nothing about it being X11-specific. The `libxcb-*` packages and Xvfb that `ci-branches.yml` installs are deliberately omitted: those load with the xcb platform plugin, and a docs build never instantiates a `QApplication`. `docs-check.yml`'s header comment said "This job needs no Qt, no Xvfb and no wavelet binary" - the opposite of what is now true - and is rewritten.
    * `quality_control.rst` gains a note that the docs build imports the real package, so a local `sphinx-build` needs `import poriscope` to work fully.

* **Fixed: a broken image on the Menus and Sessions page, visible only on Linux**
    * `menus_and_sessions.rst:27` referenced `_static/images/jsonFIle.png` while the file is `jsonFile.png`. Windows filesystems are case-insensitive, so every local build and every developer's preview resolved it; the Linux CI runner does not, and reported `image file not readable`. The published page has therefore been showing a broken image, which no local build could have caught. A sweep of every `image`, `figure`, `include` and `literalinclude` target in `docs/source` found no others.

* **Fixed: hotfix branches ran no CI at all**
    * `ci-branches.yml` triggered on pushes to `develop`, `feature/*` and `bugfix/*`, but not `hotfix/*`. A hotfix branches off `main` and `git flow hotfix finish` merges it straight back into `main` locally, so there is no pull request anywhere in that flow and none of the pull-request workflows fire either. The result was that the one branch type that goes directly to a release was the only one with no gate in front of it - the first CI a hotfix ever saw was the release run it triggered on `main`. `hotfix/*` is now in the trigger list.
    * `release/*` has the same shape and is deliberately left out for now: `ci-internal-pr.yml` already covers pull requests targeting `release/*`, so that branch type is not completely unguarded the way `hotfix/*` was.
    * `docs-check.yml` gained a `push` trigger on `hotfix/*` for the same reason, and only for `hotfix/*` - every other branch reaches `main` or `develop` through a pull request, which that workflow already covers. Without it the first docs build a hotfix ever got was `build_and_deploy_docs.yml` running against `main` after the merge, which is precisely the failure the Docs Render Check exists to catch first. A hotfix that also has a pull request open will render twice; that is a few wasted minutes on a rare branch type rather than a correctness problem.

* **Changed: `poriscope/__init__.py` no longer swallows a partial `exposed` import silently**
    * `from .exposed import *` is wrapped in `except ImportError: pass`, so that a half-installed dependency set cannot break `pip install`. The `except` is kept - but it was what turned the one-line `libEGL.so.1` failure above into several hundred unrelated Sphinx warnings, by letting the process continue with an incoherent half-imported Qt and no indication anything had gone wrong. It now logs a warning naming the failed import instead of passing.
    * This is not a breaking change: nothing is narrowed or removed, and a fully-successful import is unaffected. Worth knowing that the `pip install` rationale is largely historical - `pyproject.toml` resolves the version via `attr: poriscope.constants.__VERSION__`, and since that is a plain string literal setuptools reads it statically by AST without importing the package at all.

## Poriscope 1.7.0: 2026-08-31

* **Fixed: Load Session / Restore Session could fail with an "already exists" error if the workspace already had state**
    * `MainController.load_session` applied the loaded plugin history directly on top of whatever was already instantiated, so a plugin key or named filter already present from the current workspace collided with the same key/name in the loaded session, surfacing as an "already exists" error instead of loading cleanly. **Load Session** (a chosen file) and **Restore Session** (the last saved session) both route through this one method, so both were affected identically.
    * It now calls `reset_session()` first, so a load always starts from a clean workspace - the same one clicking Reset Session produces - regardless of what was open before it.
    * **This drops a previously-deliberate exception**: an already-open tab's live, unsaved state used to be left alone rather than overwritten by a load. That tab is now torn down like everything else before the load applies - preserving live state while also refusing to collide with saved state under the same name is exactly the ambiguity that caused the "already exists" errors in the first place, so the two could not both be kept. The now-dead "tab already open" branch in the restore loop is removed accordingly.
    * **The sidebar highlight is synced too, closing a gap this same fix would otherwise have made more visible.** `MainController.instantiate_analysis_tab` adds a tab's page and switches to it, but only the button-click handlers that normally trigger tab creation (`on_raw_data_view_click` and similar) ever synced the sidebar highlight - not this method itself. `load_session` calls it directly, bypassing those handlers entirely, so after a load the sidebar was left showing nothing (`reset_session` having just cleared it above) or whatever was highlighted before, with no tab actually behind it. `instantiate_analysis_tab` now syncs the sidebar to the new tab's own view itself, so every path that creates a tab ends with the sidebar correctly reflecting it.
    * **The status/log panel now names what was loaded.** `reset_session()` above already leaves its own message there clearing the previous workspace, but nothing said what, if anything, replaced it. `load_session` now adds "Loaded session from `<file>`." for a chosen file, or "Restored last saved session." for Restore Session (`file_name=None`), so the two are distinguishable in the panel.
    * 3 tests added (reset runs before anything is restored; the loaded file name is displayed; Restore Session's own message is displayed), 1 rewritten (the test documenting the old "leave an already-open tab alone" behavior now covers the new "tear it down and restore fresh" one instead), 1 extended (a failed load does not trigger a reset for nothing), and 1 more added for the sidebar sync itself (a newly created tab's view is highlighted; an already-open tab's is not re-synced).

* **New Dev Tooling: `setup_hooks.py` now sets the git flow release tag prefix**
    * `gitflow.prefix.versiontag` was left at its empty default, so `git flow release finish 1.7.0` would have created a bare `1.7.0` tag - which does not match `release.yml`'s `tags: ['v*']` trigger, and is how the older `1.5.0` tag came to disagree with the `v1.6.0` and `v1.6.1` ones after it. `scripts/setup_hooks.py` gained a `configure_gitflow` step that sets it to `v`, so the plain `git flow release finish <version>` command tags `v<version>` with no extra flags. It reports and leaves the value alone if it is already set to something other than `v`, rather than clobbering a deliberate choice.
    * This lives in the setup script rather than in the repository because git config, like git hooks, is per-clone and not version-controlled - so a fresh checkout must run `python scripts/setup_hooks.py` before cutting a release. `developer_setup.rst` and `CLAUDE.md` now say so.
    * Worth knowing for release day: with the tag matching, pushing `main` and pushing the tag are two separate `release.yml` triggers on two different refs, and the workflow's `concurrency` group is keyed on the ref, so neither cancels the other. Pushing both at once starts two runs.

* **Fixed: 19 routine states were logged at ERROR, and so raised a modal dialog each**
    * Follow-up to the `QtHandler` severity work below, which stopped log severity deciding *whether* to interrupt the user but deliberately left the individual levels alone. Since `QtHandler` now floors at `ERROR`, a `logger.warning` interrupts nobody - so the sites that still did real harm were the routine conditions logged at `ERROR`, each of which is a dialog. Those are fixed here. The 109 `logger.warning` sites are untouched: re-levelling them is log-signal tidiness rather than a defect, and stays recorded in `future_fixes.md`.
    * **Typing in a range box could raise dialogs.** All six `logger.error` calls in `float_range_line_edit.py` are parse or empty-input conditions on user-typed text, and one of them fires from `FloatRangeValidator._validate_final`, which `BaseValidator.validate` calls on *every keystroke* where the line edit lacks focus. One logged ERROR for an empty text box. All six are now `debug`, matching the sibling branches in the same two methods that already used `debug` for exactly the same class of condition. `RawDataView`/`EventAnalysisView`'s "Event index input is empty." went the same way.
    * `BaseValidator.validate`'s blanket `except Exception` dropped from `error` to `warning` with `exc_info=True`. The `except` itself stays - an exception must not escape a `QValidator` into Qt's C++ caller - but a defect on that path would otherwise raise one dialog per character typed. It now carries a traceback, which it did not before.
    * **One dialog per channel.** `RawDataView`'s two per-channel "No data loaded for channel N, skipping" notes sit inside a loop over the selected channels and were logged at ERROR, so plotting a run where several channels had no data raised a dialog for each one. Now `debug`; the post-loop message below covers the user-visible outcome.
    * **Empty-state guards now report on the message panel instead of as a dialog.** Nine sites where the user asked for something and there was nothing to do it with - "No data available for plotting"/"for psd calculation" (`RawDataView` twice, `EventAnalysisView`), "No clusters defined, unable to merge" (`ClusteringView`), "No experiments or channels in scope" (`MetadataView`), and "No database loader selected" (`MetadataView` and `ProteinView`, twice each) - swap the `logger.error` line for an `add_text_to_display.emit`, which is the documented place for something the user should be *told* rather than interrupted by, and is already the pattern used dozens of times in these same files. `MetadataView` in particular already sent the semantically identical "no experiments or channels in scope" condition to the panel a few hundred lines away; the two now agree. The two loader messages are reworded to "No event database selected", matching the combo box the user actually has to touch.
    * Deliberately left at ERROR: `main_model.py`'s plugin-import failure (a genuinely broken plugin is worth interrupting for, and it is the only signal the user gets), `ClusteringView`'s "dataframe came back empty", and `SQLiteDBLoader`'s missing-`id`-column check.
    * No test changes were needed - the full `tests/unit/views`, `tests/unit/utils` and `tests/e2e` trees pass unchanged, so none of the existing `logger.error` assertions sat on any of these paths.

* **Fixed: a user plugin silently replaced a built-in of the same filename**
    * `MainModel.populate_available_plugins` walks `poriscope/plugins/` and then the user plugin folder into one flat map keyed by the plugin's class name, which is also its filename stem. Both the class assignment and the menu-list `append` were unconditional, so a user `ClassicBlockageFinder.py` overwrote the shipped one with no warning, no log line, and no way to tell which of the two had actually run - a reproducibility problem, since a result could not be attributed to a known implementation. The duplicate `append` also put the name in the menu twice, both entries resolving to the same (user) class.
    * Discovery now keeps a set of the plugin names already claimed and logs at ERROR - which `QtHandler` raises as a dialog - for any later file claiming a name that is taken, skipping it. **The first file found wins, which means a built-in can no longer be displaced by a user plugin of the same name**; the user is told which file was ignored and that renaming it will load it. The check is keyed on the name alone rather than per metaclass, because plugin names are unique across the whole application - the menus and `DataPluginController`'s key-uniqueness check both rely on that - and a collision across two different metaclasses was the quietest variant, leaving both classes live under one name in two different menus.
    * Not included, deliberately: `load_plugin` still calls `exec_module` on every `.py` file before checking whether it holds a plugin at all, and still does not register modules in `sys.modules`. Both are recorded in `future_fixes.md`.

* **BREAKING: `QtHandler` no longer raises a dialog for every `WARNING`, and no longer inherits the root logger's level**
    * `QtHandler` sat on the root logger with no level filter, so log severity doubled as a decision about how much to interrupt the user - all 112 `logger.warning`, 161 `logger.error` and 16 `logger.exception` sites under `poriscope/` were dialog-capable. Routine states hit it: `send_analysis_tabs`' "No instantiated analysis tabs found" is true at every cold start, `populate_available_plugins`' skipped-directory warning fires while the main window is still being built, an empty text box logged at ERROR, and the just-merged `restore_subset_filters` added a warning on the session-load path. The handler now defaults to `ERROR`. **Breaking**: `QtHandler` is re-exported from `poriscope/exposed.py`, its constructor takes a new `level` argument (defaulting to `logging.ERROR`), and anything relying on it to surface warnings will no longer see them.
    * **`MainModel.update_logging_level` now skips `QtHandler`** when applying a level to the root logger's handlers. * **BREAKING: `BaseDataPlugin.lock` is now a per-instance lock, not a class attribute**
    * It was `lock = threading.Lock()` at class-body scope, i.e. **one lock shared by every data plugin instance of every type in the process** - readers, filters, writers, fitters and loaders all contending on the same object. It is now `self.lock = threading.RLock()`, created in `__init__` before `_init()` so subclass hooks can rely on it. Any external code doing `SomePluginClass.lock` (class-level access) breaks; `self.lock` inside a plugin keeps working but now means "my lock" rather than "everyone's lock". Reentrant on purpose: the guard goes into base classes that plugin authors subclass, and a plain `Lock` re-acquired by the thread already holding it hangs silently rather than raising.

* **Fixed: `force_serial_channel_operations()` was enforced at the wrong granularity**
    * The declaration is per-plugin, but the lock handed to the worker was `MetaModel.lock` - scoped to the *model*, of which every analysis tab builds its own. Data plugin instances live in one global registry and are resolved by `(metaclass, key)` string, so **two tabs resolve the same writer to the identical Python object while supplying different locks** - it ran concurrently on two channels despite `MetaWriter` and `MetaDatabaseWriter` both declaring `True`. In the other direction, within one tab that single lock was shared across all plugin keys, so unrelated plugins serialised against each other for nothing.

The lock is held for the whole run of the generator, which is the same span the worker used to lock - what changed is whose lock it is, not the serialisation semantics.

* **Fixed: a `TypeError` inside any plugin generator was reported as a successful run**
    * `Worker.process_generator` drove every generator with `send()` and absorbed `TypeError` with a blanket `except TypeError: next(self.generator)`. That arm is needed on iteration one - `send()` on a not-yet-started generator raises `TypeError` by design - but it could not tell that case apart from a `TypeError` raised inside the generator *body*. By then the generator is already closed, so the `next()` fallback raised `StopIteration` and the loop logged `"Generator finished StopIteration."` at **INFO**. The original exception, its message and its traceback were discarded with no record at any level; `TypeError` was the only exception type this loop swallowed silently.

Not theoretical: `MetaEventFitter.fit_events` documents `:raises TypeError:` and raises it at three points inside its per-event loop, i.e. after the first yield and squarely in the masked regime. Any accidental `TypeError` from plugin arithmetic landed the same way.
    * The generator is now primed with one explicit `next()` and driven with `send()` on every iteration after that, so there is no `except TypeError` arm left to mask anything. **Behaviour on the happy path is unchanged** - iteration one already ended up in `next()` via the `TypeError` bounce.
    * **The four typed `except` arms collapsed into one `except Exception`.** `RuntimeError`, `ValueError` and `IOError` differed from the catch-all only in wording and log level, and all four ended the run identically - and `IOError` is an alias of `OSError`, so it was never distinct anyway. Per-type special-casing in this loop is what allowed the bug, so the fix removes the whole category rather than the one instance. `StopIteration` keeps its own arm because it is the success path.
    * **Every exit arm now emits its progress-bar completion value explicitly** rather than leaning on the `finally` in `Worker.run`, and does so *before* logging the failure. The teardown travels on a queued connection while an ERROR record raises a modal dialog, so emitting first is what stops the progress bar being stranded behind that dialog. Verified: pre-fix the failure path emitted only `50.0` and no completion at all from the loop.
    * Also removed an inert `except Exception: raise` in `Worker.run`.

* **The signal-bus dispatcher no longer guesses: reflection replaced the `TypeError` retries**
    * `MainController.handle_global_signal` wrapped every plugin call in `except TypeError: func(None)` as arity recovery. That cannot tell a signature mismatch at the call boundary from a `TypeError` raised inside the callee, so a method that had already run was called a second time with different arguments. It existed to guess how an ambiguous payload should be unpacked. With every emit site now passing a real tuple and the return value decided by annotation, there is nothing left for it to guess at. `_can_bind` is a pre-flight diagnostic only - nothing routes on it.
    * A callee that declares a tuple return and produces something else is now logged and its value passed as a single argument rather than coerced, since `tuple()` would silently shred a string and raise on `None`.

* **New: Reset Session, under File, returns the app to a freshly-launched state**
    * Sits with Restore / Save / Load Session, because it is a session verb rather than a setting. It deletes every instantiated data plugin, closes every analysis tab, clears both in-memory histories and returns to the landing page - the state you get launching Poriscope from scratch, without quitting and starting it again.
    * **The saved session files are left on disk, and that takes active effort.** Both histories persist themselves on every change, and deleting a plugin emits one history update per plugin, so the teardown would otherwise have written an empty session over the file before the user could restore from it. A `_suppress_session_save` guard, held across the teardown in a `try/finally`, keeps the file as it was.
    * **Restore Session's existing limitation applies, and the dialog indicates so.** `plugin_history.json` is a live mirror rewritten on every plugin or tab change, and the in-memory history is empty after a reset, so the next thing the user sets up overwrites what Restore would have read. This is **not introduced here** - it is equally true after launching the application, where the in-memory history also starts empty and the first tab opened replaces the previous session. Reset imitates launch faithfully, including this. The prompt states the condition rather than the code papering over it, and no behaviour of Restore Session was changed.
    * **Running workers are stopped before anything is deleted**, as they are on quit. Deleting a plugin calls `close_resources()` on it, so a worker still running against one would be reading from a file handle that has just been closed. `exiting=True` is passed for the same reason quit passes it - it blocks until each thread actually finishes rather than only signalling it - even though the application is not exiting. A test pins the ordering, since killing workers after the delete would achieve nothing.
    * **An active walkthrough is cancelled first.** `switch_to_page` refuses to move while a walkthrough or milestone is in progress, so the return to the landing page was silently ignored if someone reset mid-walkthrough - leaving them on a page the teardown had just destroyed, with a stale title. `MainView.cancel_walkthrough()` is extracted from the teardown `_on_milestone_closed` already performed, so there is one cleanup path rather than two, and reset calls it before removing the pages.     * Now is able to run safely in multiple threads

    * Has been added.

    * Allows export of subsets into human-readable CSV format.

    * Allows specification of time limits for event finding.
* **Updated Frontend Plugin: `EventAnalysisView`**
    * Now allows plotting of horizontal and vertical lines on plots to highlight features of interest

### Deprecated:

* `BinaryEventWriter` has been removed to enforce consistent file formats internally.

### Notice of Future Deprecation:

* `BinaryEventLoader` will be deprecated in a future release. Please convert any datasets written with BinaryEventWriter to the new SQLEventWriter before the next release. 

### Optimization:

* `SQLEventWriter` has been heavily optimized for speed.
* `SQLDBWriter` has been heavily optimized for speed.

### Metaclass Update:

* **`MetaEventLoader` and `MetaEventWriter`**
    * Have had updates to their interface to change the structure of databases.
* **`MetaDatabaseWriter`**
    * Now enforces inclusion of raw data, filtered data, and fitted data in the database.
    * Allows writing from plugins with different metadata to the same common database.
    * *Note: Missing values will be null.*
* **All Data Metaclasses**
    * Can now enforce serial channel operations through a flag if necessary.
    * Metaclasses that create generators that are operated on by the GUI (these being `MetaEventFinder`, `MetaEventFitter`, and `MetaEventWriter`) now allow internal early abort of the generator through provision of a flag to the generator.

* **All Frontend Metaclasses** 
    * Now set an abort Boolean and allow abort and cleanup to be handled internal to the plugin, which fixes a bug in which threads were not being properly canceled when serial operations were in force. 
    * Plugin editor no longer allows changing source plugins or names for the sake of internal state consistency

### General Fixes and Improvements:

* Plugin menu position adjusted for consistency.
* Bugs relating to canceling plugin initialization have been fixed.
* Plugins that use database connections have been updated to enforce transient database connections to avoid issues with open database handles between threads.
* Miscellaneous frontend cleanup.
* Updates to reports generated when plugins are loaded and/or complete their analysis.
